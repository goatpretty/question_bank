## 3. 详细发现与修改建议

### A01 / P0：环境文件没有安全发布边界

**证据。** `.env` 中填写了 `SMTP_PASS`、`AI_API_KEY` 等敏感配置；只确认存在配置值，没有向服务商验证其有效性。`JWT_SECRET` 的本地值具有示例字符串特征。当前 `.gitignore` 只排除了常见构建、依赖和编辑器文件，没有排除 `.env`、`.env.production`、数据库、备份或验收材料。`.env.example` 只有数据库和 SMTP 配置，缺少安全启动所需的 JWT 配置。

**影响。** 直接执行初次 `git add .` 可能把邮件授权码、AI 凭据和部署信息一起提交。前端构建时还需注意：`VITE_*` 变量会成为浏览器可见配置，不能放服务端秘密。Supabase anon key 本来就是客户端可见配置，不能把“发现 anon key”直接等同于管理员密钥泄露；其安全性还取决于后端 RLS 与权限策略，本次没有验证远端策略。

**修改。** 添加环境文件忽略规则，仅保留经过检查的示例；对密钥、数据库 URL、运行模式和来源白名单做启动校验。服务端 JWT 密钥缺失时应拒绝启动。示例中补全必需变量，SMTP、AI 等可选能力应明确关闭方式。

**验收。** 在单独准备的发布仓库中检查实际待提交清单，并扫描整个待发布历史。若某个有效凭据已经进入外部仓库、共享包或镜像，需撤销/轮换并清理历史；仅增加 `.gitignore` 不会移除已有提交。

### A02 / P0：运行数据通过多个渠道进入发布内容

**证据。** 以只读方式检查当前 `api/data/question-bank.db`，包含 10 条用户记录、1,514 道题、53 条考试提交、359 条练习会话、3,481 条练习答案、573 条错题明细。用户表包含邮箱和 `password_hash` 字段。`api/data/users.json` 另外有 6 条用户记录。

`api/data/` 共 23 个文件，约 142 MB，包含 20 个历史数据库备份；`.codex-backups/` 另有约 41 MB 的源码、构建及数据库副本。`docs/round4-evidence/history-preview/full-preview.json` 的字段包含用户标识、用户名、会话、作答、正确答案及题目快照。相关日志、截图和其他 JSON 也应作为运行材料审查，不能仅删除主数据库。

另有两条分发路径：`Dockerfile` 明确执行 `COPY --from=base /app/api/data ./api/data`；`.github/workflows/ci-cd.yml:49` 的构建产物上传范围包括整个 `api/`。

**影响。** 密码哈希仍是敏感数据，用户标识、时间和作答快照也可能关联个人。数据库备份、公开 Actions 工件和公开镜像都可能形成泄露渠道。

**修改。** 开源包只保留应用源码、必要迁移及经过授权的合成样例。排除数据库及 `-wal` / `-shm` 文件、备份目录、运行验收资料、凭据临时文件和部署状态文件。保留有价值的技术文档时，应使用合成数据替换真实示例；截图应逐张检查。

**验收。** 分别检查 Git 待发布文件、Docker 构建上下文及最终镜像、CI 工件、Release 附件。生成演示数据应从空库建立，不能依赖复制运行库后删除几张表。

### A03 / P0：认证有效期和令牌用途隔离不成立

**证据。**

- `api/config.ts:4` 使用公开固定字符串作为密钥缺失时的后备值。
- `api/routes/auth.ts:271`、`:416`、`:510` 的登录/注册签名没有 `expiresIn`。
- `api/middleware/auth.ts:34` 以及改密/重置分支使用 `ignoreExpiration: true`。
- `api/routes/auth.ts:742` 签发 15 分钟重置令牌，但 `:1112` 的验证又忽略过期。该分支没有持久化的一次性消费状态。
- 通用认证中间件只做签名校验及类型断言，没有验证令牌用途、`id`、`role`，也没有查询当前用户或会话版本。

**复核。** 使用合成密钥和过期的合成管理员 JWT 调用当前认证中间件，确实进入 `next()`。用合成密码重置 JWT 调用同一中间件也被接受，尽管它没有用户 ID 和角色。没有对真实账号执行请求。

**影响。** 令牌泄露后的使用窗口不受预期过期时间约束；修改密码不会自动使旧令牌失效；重置凭据有长期重放风险。将不同用途的 JWT 当成登录凭据还可能破坏依赖用户 ID 的查询边界。例如 `api/routes/exams.ts:255` 从令牌直接取 ID，`:260` 将其用于查询，需防止缺失 ID 导致范围校验失效。本次没有对真实数据执行该越权路径。

**修改。** 移除后备密钥，设置并严格校验访问令牌有效期；区分访问、重置和业务确认令牌的用途、受众及必要字段。重置令牌应短期且一次性使用，并绑定密码版本或单独的消费记录；改密、重置和权限变更应使旧会话失效。认证通过前应核验当前用户和角色状态。

**验收。** 过期、错误用途、缺少 ID/角色的 JWT 一律被拒绝；重置令牌第二次使用失败；改密或降权后旧令牌不能继续访问原权限接口。

### A04 / P0：存储型脚本执行与明文密码持久化形成高风险组合

**证据。** `src/components/MathRenderer.tsx:59` 将未经 HTML 清洗的题干/内容直接写入 `innerHTML`；`:34`、`:48` 开启 KaTeX `trust: true`。该组件用于练习、考试、错题和管理预览等页面。`src/stores/auth.ts:59` 保存登录密码，`:300` 又把 `lastLoginPassword` 纳入 Zustand 持久化，写入 localStorage。访问令牌也保存在同一浏览器存储中。

**复核。** 在内存 JSDOM 中执行当前组件，用只设置本地标记变量的合成 HTML 事件验证，脚本能够执行。使用模拟登录服务执行当前 auth store，确认合成明文密码进入 `auth-storage`。没有写入恶意题目，也没有读取真实浏览器存储。

**影响。** 恶意题库、导入内容或其他被渲染的非可信内容可能触发脚本。当前数据流还会扩大为密码和会话被读取的风险。

**修改。** 移除明文密码的持久化和长期内存保留；对现有浏览器状态执行版本迁移以删除旧密码字段。普通文字应转义，确需富文本时采用严格允许列表清洗；公式默认关闭 `trust`，有必要时只允许明确支持的命令。清洗不能只检查 `<script>` 标签，还需覆盖事件属性、危险 URL 和其他 HTML/SVG 输入。

**验收。** 历史 `auth-storage` 在升级后不再保留密码；恶意事件属性和危险 URL 被移除；正常题干、选项、换行和公式仍正确展示。CSP 可以作为附加防线，不能替代输出清洗。

### A05 / P1：许可证声明缺少实际授权文件

**证据。** `README.md:200` 声称采用 MIT 并链接 `LICENSE`，但项目中没有找到实际项目许可证文件。`package.json` 也没有项目许可字段。

**修改。** 确认拥有代码授权权利后，选择并添加完整许可证文本、版权年份及权利主体，补全包元信息。若继续采用 MIT，应检查已有贡献或复制代码是否允许以该方式分发。`private: true` 可以继续保留以防误发 npm，它不妨碍在 GitHub 开源。

依赖锁文件里的生产依赖许可主要是 MIT、Apache-2.0、ISC 和 BSD 系列，未发现仅凭这次元数据检查就能认定的强 copyleft 冲突。3 个包在锁文件中缺少许可字段，这不代表它们无许可证，仍应检查包内许可原文。分发打包前端、字体或镜像时应保留相应许可和必要归属信息。

**验收。** LICENSE、README 和包元信息一致；代码、题库、图标/字体等资产的许可范围清楚；第三方归属有可追溯记录。

### A06 / P1：题库来源记录不能替代再分发授权

**证据。** `docs/毛概-新增/` 中保留原始题目、转换稿、导入 JSON、来源映射和既有题库快照。当前运行库中共有 1,514 道题。已有材料能够说明部分内容如何转换和导入，但没有找到覆盖这些题目、解析及原始资料的明确公开再分发许可证明。

**影响。** 对应用代码采用 MIT，不会自动取得第三方教材、学校题库或整理材料的再分发权。用户授权将题目导入本地系统，也不能直接推导为版权所有者授权公开传播。

**修改。** 建议首发以“题库管理与学习系统源码 + 自编合成题目”交付。现有题库默认不随仓库发布；希望公开的内容逐项确认权利人、来源、许可、署名、修改及再分发条件，并单独声明数据许可。内容出处明确但授权未核实的，继续保留在本地。

**验收。** 每份随仓库发布的数据都有可核验许可或作者原创声明；排除的题目不会通过测试样例、导入快照和截图重新进入仓库。本项属于授权证据缺口，本报告不作侵权认定。

### A07 / P1：第三方不能按现有说明从空目录启动

**证据。**

- 生成的 Prisma 客户端被 `.gitignore` 排除，但 `package.json`、README、CI 和 Dockerfile 没有安排 `prisma generate`。
- 在不含生成客户端的源码副本中执行类型检查，出现多处缺失 Prisma 导入错误；手动执行 `prisma generate` 能成功。
- 当前两份 Prisma SQL 迁移仅创建错题相关表。在内存空库执行全部迁移后，只有 `wrong_book_occurrences`、`wrong_book_collection_jobs`、`wrong_book_backfill_runs`，没有 `users`、`questions` 等基础表。
- `api/db/prisma.ts:10` 在创建适配器前对数据库文件执行 `realpathSync`，文件不存在会先失败。
- `scripts/exam-lifecycle-integration.ts:12` 等集成脚本从现有运行库读取表结构，再建立测试库，不能独立于运行库复现；脚本使用的系统临时库路径又与 `api/db/prisma.ts:13` 的项目内路径限制冲突。

**修改。** 补全 schema 到空库的初始化基线、Prisma 生成命令和演示 seed；增加安全的首次管理员初始化方式。明确选择正式 migration 流程还是仅用于开发的 `db push`，不要让二者和自定义迁移互相覆盖。测试应从已提交 schema / migrations 建库，路径策略应允许明确的隔离测试目录。

**验收。** 在没有环境文件、真实数据库、生成客户端和本地备份的干净副本中，安装、生成客户端、初始化数据库、创建管理员、启动和测试全部成功。

### A08 / P1：后端生产构建和启动链路中断

**证据。** `npm run build:server -- --noEmit` 未通过：`api/check_punct.ts:1` 缺少 `better-sqlite3` 类型声明；`api/routes/questions.ts:1003` 等 4 处访问可能为 undefined 的 `options`。

在临时副本中执行实际后端编译，还确认 `api/tsconfig.json` 的 `rootDir: ".."` 与 `outDir: "../dist/api"` 组合把入口输出到 `dist/api/api/server.js`，而 `npm start` 和 Docker CMD 指向 `dist/api/server.js`。直接运行实际输出入口继续出现 `ERR_MODULE_NOT_FOUND`，指向无扩展名的 `emailVerifier` 导入。

**修改。** 修正类型错误，把临时检查脚本移出生产编译范围，统一输出目录与启动命令。服务端统一使用兼容 Node ESM 的模块解析和文件扩展名，必要时使用 NodeNext 或明确的打包方案。构建应禁止错误产物被当成成功制品。

**验收。** 干净环境下 `npm run build:server` 成功，使用构建产物而非 tsx 开发入口启动，健康检查及基本认证/数据库访问成功。

### A09 / P1：默认质量入口和 CI 无法作为发布依据

**实测。**

| 检查 | 结果 | 解释 |
| --- | --- | --- |
| 当前工作目录 `npm run check` | 通过 | 本地已有生成客户端；主 tsconfig 的严格检查较宽松。 |
| 后端严格类型检查 | 失败 | 5 条诊断；见 A08。 |
| `npm test -- --runInBand --silent` | 失败 | 11 个 suite 中 5 个通过、6 个失败；成功执行的 38 个测试通过。 |
| 专用 learning-flow Jest 配置 | 通过 | 5 个 suite、80 个测试通过；该配置关闭 ts-jest diagnostics，不能替代类型检查或完整测试。 |
| `npm run lint` | 失败 | 23,481 errors、1,020 warnings；扫描包含 `.codex-backups` 等本地材料，不应把总数理解为有效源码的独立缺陷数。 |
| 不含生成客户端的源码副本类型检查 | 失败 | 缺失 Prisma 客户端；手动生成后具备后续构建条件。 |
| 隔离副本 `vite build` | 通过 | 未复制真实 `.env*`；只说明前端构建成功，不代表应用生产启动成功。 |

默认 Jest 故障包括 React 导入设置、`import.meta` 转换、旧 auth 测试调用签名、TextEncoder 缺失和 CSS 模块处理。ESLint 未排除生成客户端和本地备份，还强制 Windows 换行；应统一跨平台换行策略和检查范围，避免平台噪声。

### A13 / P1：部署方案不能直接复用现状

**Docker。** 没有 `.dockerignore`，两个 Dockerfile 都使用 `COPY . .`，会把运行配置、备份等送入构建上下文；后端最终镜像还直接复制运行数据库。后端镜像复制全部 node_modules，未整理生产依赖和非 root 身份。A07、A08 的客户端生成、类型错误、输出入口问题也会影响镜像。此次没有执行 Docker build，不把静态检查当作镜像运行验证。

**Vercel。** 当前 Prisma 适配器明确只接受本地 SQLite 文件（`api/db/prisma.ts:9`），并限制为项目内既存路径。这样的运行数据持久化方式不适合直接作为 Vercel 无状态函数上的 SQLite 方案；README 的“生产 PostgreSQL”也不是当前实现支持的切换能力。若保留 Vercel，建议作为前端部署方案，后端放到具备持久化存储的环境；切换远端数据库则需要单独实现和验证。

**环境与 API 地址。** README 写 `CORS_ORIGIN`，实际 `api/server.ts:48` 读取 `FRONTEND_URL`；README 写 `JWT_EXPIRES_IN`，当前认证没有使用它；README 的 SQLite URL 示例与当前 `file:` 限制不一致。`src/services/authService.ts:20` 等直接使用 `/api/auth/...`，而其他服务使用 `VITE_API_URL` 构造的 `apiBase`，前后端分域时会出现认证和业务接口目标不一致。

**版本。** README 声称 Node.js 18+，本地 Prisma 7.8.0 声明要求 `^20.19 || ^22.12 || >=24.0`，better-sqlite3 也不支持 Node 18。应以实际测试的受支持版本为准，补 engines 和版本文件，并统一 CI 与容器版本。

**修改与验收。** 先选择一条正式支持的部署路径，建立空库/持久卷和首次管理员流程；Docker 仅复制必要源码和构建输出，不携带本地运行数据。验证真实构建产物启动、前端登录及完整 API 调用、容器重启数据持久化、反向代理下的限流及 CORS，再将该路径写入 README。

### A14 / P2：细化上传、查询与 AI 的资源控制

**证据。** `api/routes/questions.ts:10` 使用无大小/文件数限制的内存 multer。`api/server.ts:54` 的 JSON 10 MB 限制不能替代 multipart 上传限制。题库列表 `api/routes/questions.ts:65` 查询符合条件的全部题目，再在内存过滤分页；全局限流跳过 GET。`api/routes/ai.ts:95` 外部请求没有显式超时和取消，题目上下文没有与聊天消息同等级的长度约束，也没有每账号额度/并发控制。已有消息数、单消息长度、输出 token 和生产全局限流，不能把它描述成完全无限制。

**修改。** 限制文件字节数、数量、字段及表格行列数；对分页和筛选做输入校验并尽可能在数据库分页。AI 增加超时、并发、用户额度、停用开关和成本监控，默认可选关闭。按可信反向代理设置 IP 解析，不直接信任所有转发头。

AI 请求会把用户提问和题目上下文发送给所配置的外部服务。公开演示应向使用者说明发送内容、服务提供方及适用的数据处理方式；题库再分发授权之外，也需考虑是否允许把相关内容交给第三方处理。不要把实际运行密钥或个人专用服务配置写成必须使用的默认值。
